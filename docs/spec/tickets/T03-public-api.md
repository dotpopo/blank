# T03 · 公开 RPC 层与类型化客户端

| | |
|---|---|
| 依赖 | T01 |
| 阻塞 | T05, T06, T08, T09 |
| 预估会话数 | 1 |

## 目标

让前端**只有一个地方**能和数据库说话。
所有组件都调这一层,不直接碰 `supabase.rpc(...)`,更不碰表。

## 交付物

- [ ] `src/api/` 下按域拆分的模块: `pool.ts` / `apps.ts` / `admin.ts`
      > **偏离。实际是 `src/data/`: 一个接缝接口 + 两个适配器(演示/Supabase)。比按域拆模块更贴 D-1 的数据源可切换**
- [x] `src/types/` 下与 RPC 返回值一一对应的类型(zod schema + 推导出的 TS 类型,
      模板已带 `zod`,用起来)
- [x] 统一的错误映射: 把 Postgres 的错误码翻成**面向用户的中文文案**,
      而不是把 SQL 错误抛到界面上
- [x] `src/lib/supabase.ts` 补齐: 从 `import.meta.env` 读 URL 与 anon key,
      缺失时给出**可执行的**报错(告诉用户去改哪个文件)
- [x] 每个 API 函数返回 `{ ok: true, data } | { ok: false, error }`,不用抛异常驱动流程

## 约定

- 所有函数是**纯数据进出**,不在这里做 UI 状态。
- 不在这一层做配额判断(那是 T07,本地层)。
- 不缓存。需要缓存时由调用方或 zustand 处理。

## 验收

- 每个 API 函数有一个最小的调用示例(可以是 `tests/` 下的一个测试,或 `docs/` 里的片段)。
- 断开网络时,函数返回 `{ ok:false }` 而不是抛未捕获异常。
- `npm run build` 通过,无 `any` 泄漏到组件层。

## 不做什么

- 不写组件。
- 不做请求重试/缓存/乐观更新(按需在后续工单里加)。
