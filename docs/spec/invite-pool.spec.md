## 1. 一句话目标

一个**匿名的邀请码流转池**。任何人把手里富余的邀请码丢进去,任何人一键取走一个。
没有账号,没有登录,前台只暴露「池子里现在还有多少」和「它流动得有多快」。

## 2. 要解决的问题(我的复述)

邀请码是一种**易腐、稀缺、且高度分散**的东西。它有三个同时存在的毛病:

1. **散**: 它散落在群聊、私信、论坛回复、评论区。发出去十分钟就被刷没了,后来的人根本看不到。
2. **有富余但没有倾倒口**: 一个产品发给持有者 5 个码,他只用 1 个。剩下 4 个的处境是:
   发群里会被秒抢(且给不到真正需要的人)、单独发给朋友可能对方用不上、自己留着就等它过期。
   他缺的不是「分享的意愿」,而是一个**足够轻的倾倒口**。
3. **有需求但没有取用口**: 需要码的人要到处问、要动用社交关系、要蹲点。他缺的也不是「意愿」,是**一个不用求人的入口**。

这三条合起来造成一个荒谬的结果: **大量邀请码在无人知晓的情况下过期作废,同时另一些人在到处求码。**
供需两头都在,中间的通道是断的。

所以真正的矛盾不是「怎么把库存管住」。是 **「怎么让一次给予、一次取用,轻到人们愿意顺手做一次」**,
同时让这个池子的健康度**可见**(新增与消费的差额、一个码从入池到被领走要多久)。

你的取舍很明确: **放弃强身份约束,换这个「轻」**。
不设账号、不设邮箱、不设验证码;不靠 IP 限流;明说「不要在意被薅空」。
配额只做「浏览器本地计数」这一层,目的是**让随手薅变得麻烦**,而不是防住它。

这个取舍我认为是对的,理由写在 11.1。

## 3. 用户与核心场景

池子里只有三种角色,**全部匿名**:

| 角色 | 身份 | 能做什么 |
|---|---|---|
| 给予者 | 匿名浏览器 | 给**已上架**的应用贡献邀请码;给一个**尚不存在**的应用提交上架申请(待审) |
| 领取者 | 匿名浏览器 | 从「最新 20 条」里一键领取并复制;或用「骰子」随机取一个 |
| 管理员 | 固定账号(用户名+密码写在数据库里) | 审核新应用、设应用有效期、硬删除、看大盘 |

**核心场景(按重要性排序)**

- **S1 空手而来,拿到一个能用的码。** 打开首页 → 看到池子总数和最新 20 条 → 点一条 → 码自动进剪贴板 → 提示「已领取,剩余额度 2/3」。
- **S2 手里有富余,顺手倒掉。** 点「贡献邀请码」→ 选应用(或搜不到就新建) → 粘贴码 → 设有效期(默认取应用的有效期) → 提交。已上架应用**立即入池**。
- **S3 带来一个新应用。** 提交的应用在库里不存在 → 进待审队列 → 前台提示「已提交,审核通过后你的码会自动入池」。
- **S4 管理员开门。** 登录 → 待审队列 → 通过/驳回 → 通过时设该应用的有效期 → 该应用下所有待入池的码一次性生效。
- **S5 看大盘。** 首页或大盘页看到「新增 vs 消费」的趋势线、当前池子净量、以及**码被领走的快慢**。
- **S6 骰子。** 点骰子 → 从池子里随机取一个(见 11.4 的加权建议) → 同样扣配额。

## 4. 设计概念 (Design concept)

一句话: **这不是一个「商城」,是一个「水位计」。**

- 前台**不列库存**,只报**水位**:池子总数 + 最新 20 条可领。用户的心理模型应该是「这里在流动」,不是「这里有货架」。
- 一个邀请码**被领走就从池子里消失**(决策 D-2)。
  它不会被「标记为已领」然后继续挂在墙上,因为挂着的已用码对任何人都没有价值,只会让水位计说谎。
  当前阶段不接数据库,所以这条先落在演示适配器的行为里;真实删除语义等接入真实数据源时再定。
- 前台**唯一需要用户付出成本的动作是「领取」**,所以整个页面的视觉权重应该压在:
  水位数字、剩余额度、以及那一个领取按钮上。其余全部降噪。
- 大盘是**给池子的,不是给用户的**。它存在的意义是让「供需是否失衡」一眼可见,
  所以它只画两条线(新增、消费)加一条净量,不堆图表。

## 5. 关键决策 (ADR 摘要)

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| D1 | 后端用 Supabase Postgres,**anon 角色不给表级 SELECT** | 否则一次请求就能把整表抓走,「前台只显示池子总数」只是装饰 | 所有读都要走 RPC,开发稍慢 |
| D2 | 领取/贡献/骰子全部走 `SECURITY DEFINER` RPC | 领取必须是原子的(取一个、删一个),并发下不能两个浏览器领到同一个码 | RPC 需要仔细写权限与参数校验 |
| D3 | 配额存 `localStorage`,key 含日期 | 你明确不要 IP、不要账号。localStorage 清得掉,但清掉是「主动行为」而非「顺手行为」 | 配额可被绕过,接受 |
| D4 | 密码用 **bcrypt**,浏览器端生成 | Postgres 的 `pgcrypto` 原生有 `crypt()`/`gen_salt('bf')`,服务端校验只需一行 SQL,不用写 Edge Function | 生成器页面需引入 bcryptjs(见 T02) |
| D5 | 新应用**待审**,新邀请码**免审** | 码的价值在于快,审了就凉了;应用分类的价值在于稳定,不审就烂 | 待审队列会给管理员带来持续负担 |
| D6 | 过期码不进池子(查询层过滤),不做后台定时任务 | 查询时 `expires_at > now()` 过滤即可,零运维 | 过期码留在表里占空间,由管理员定期硬删 |
| D7 | 测试用 tester.army/e2e,模型走 `LLM_*` 三个用户环境变量 | 你的要求。配置一次写在 `e2e.config.ts` 里读 `process.env`,不用每次 export | 依赖 agnes 网关支持 tool calls + 图片(待验证,见 T10) |

## 6. 数据模型(草案,由 T01 落成 SQL)

```
apps
  id             uuid pk
  slug           text unique          -- 归一化后的标识,用于合并重复应用
  name           text
  category       text
  icon           text                 -- emoji 或图标名,不用假截图
  description    text
  url            text
  validity_days  int                  -- 该应用邀请码的默认有效期(天)
  status         text                 -- pending | approved | rejected
  submitted_at   timestamptz
  reviewed_at    timestamptz
  reviewed_by    uuid -> admins.id
  reject_reason  text

invite_codes
  id             uuid pk
  app_id         uuid -> apps.id
  code           text                 -- 明文码或邀请链接
  code_hash      text unique          -- sha256(code),用于去重(见 11.5)
  note           text
  expires_at     timestamptz          -- 默认 = created_at + apps.validity_days
  status         text                 -- available | claimed | removed
  created_at     timestamptz
  claimed_at     timestamptz
  claim_token    text                 -- 领取者的浏览器指纹,仅用于审计与举报关联

admins
  id             uuid pk
  username       text unique
  password_hash  text                 -- bcrypt, $2a$12$...
  created_at     timestamptz

pool_events                          -- 大盘的数据源
  id             bigserial pk
  kind           text                 -- added | claimed | expired | removed
  app_id         uuid
  code_id        uuid
  occurred_at    timestamptz
```

**索引**: `invite_codes(status, expires_at desc)`, `invite_codes(app_id, status)`,
`pool_events(occurred_at)`, `apps(status, submitted_at desc)`。

**RPC 面(对外只暴露这些)**

| RPC | 作用 |
|---|---|
| `pool_summary()` | 池子总数、今日新增、今日消费、今日过期 |
| `latest_available(p_limit)` | 最新 N 条**可领**条目(默认 20),返回应用信息与到期倒计时,**不含码文** |
| `claim_code(p_code_id)` | 原子领取指定码,返回码文,同时写 `pool_events` |
| `roll_dice()` | 随机领一个,返回码文 |
| `contribute_code(p_app_id, p_code, p_note, p_expires_at?)` | 给已上架应用贡献码 |
| `submit_app(...)` | 提交新应用(进 pending) |
| `pool_trend(p_days)` | 大盘趋势数据 |
| `admin_login(p_username, p_password)` | 校验 bcrypt,签发短期 admin token |
| `admin_review_app(p_token, p_app_id, p_approve, p_validity_days, p_reason)` | 审核 |
| `admin_remove_code(p_token, p_code_id)` | 硬删除 |
| `admin_pending_apps(p_token)` | 待审队列 |

## 7. 配额与约束

- **key**: `opendoor:quota:<appId>:<YYYY-MM-DD>`
- **value**: `{ claim: n, contribute: n, dice: n }`
- **上限**: 每项 3
- **重置**: 换日期即重置(所以是「每天」,见 Q2)
- **额度耗尽时**: 按钮禁用 + 明确文案(「今天的领取额度用完了,明天再来」),不是静默失败
- **服务端不做配额校验**(你明确要求不用 IP)。服务端只做**去重**(`code_hash` unique)与**速率兜底**(见 11.7)

## 8. 管理员与密码

- 固定账号。用户名与 bcrypt 哈希**直接写进 `admins` 表**(SQL 插入),不提供注册入口。
- 算法: **bcrypt,cost 12**,存储格式 `$2a$12$<salt><hash>`。
- 校验发生在 Postgres 侧: `password_hash = crypt(p_password, password_hash)`。
- 交付一个**单文件 HTML 生成器**: 输入明文密码 → 输出可直接 `INSERT` 的 `$2a$12$...` 字符串。纯前端,不联网,不落盘。
  (这是 T02 的交付物。生成器本身不进仓库的公开路径,或至少标注「仅本地使用」。)
- 会话: anon key 场景下没有 httpOnly cookie 可依赖。`admin_login` 返回短期 token,存 `sessionStorage`,
  后续 admin RPC 校验该 token。**这是弱鉴权,记录在案**(见 Q6)。

## 9. 非目标 (Non-goals)

- 不做真实账号体系、不做邮箱/OAuth 登录、不做找回密码。
- 不做邮件/推送通知。
- 不承诺邀请码一定可用。只提供「举报失效」入口(见 11.6),不自动判定。
- 不做移动端原生 App。响应式 Web 即可。
- 不做支付、不做会员。

## 11. 优化建议(对你原设计的补充)

按「值不值得做」排序。

**11.1 你的匿名取舍是对的,但配额的落点应该换一个。**
浏览器本地计数防不住任何人。它真正的作用是**给正常人一个「够了」的心理刹车**。
所以别把它当安防做,把它当**文案**做:额度用完时那句提示,比配额本身更影响体验。
(结论: 保持 localStorage 方案,但把预算花在「额度状态的可见性」上,而不是花在对抗绕过上。)

**11.2 池子最容易亏的地方不是被薅,是「静默过期」。**
一个码从入池到过期,如果没人领,这条供给就白费了。所以:
- 「最新 20 条」**不应该按创建时间排**,应该按 **`expires_at` 升序排**。让快过期的先被看见。
- 加一个**「快过期」标签**(剩余 < 24h),视觉上单独强调。
- 大盘加一个指标:**过期未领数**。这个数字越大,说明池子水位虚高。

**11.3 大盘真正的健康指标是「领走速度」,不是「总数」。**
池子总数是个会骗人的数字(靠不断新增堆出来的)。
建议的核心指标: **`中位领取时长`(median time to claim) = 码从入池到被领走的中位耗时**。
- 中位数是**分钟级**: 供给不足,池子在被饥饿消费。
- 中位数是**天级**: 供给过剩,该做的是「提醒持有者别囤」而不是拉新。
这一个数字比十条曲线有用。

**11.4 骰子应该是加权的,不是均匀随机的。**
均匀随机等于「再抽一次最新 20 条」,没有独立价值,还会让最新的码被反复抽走、临期的码继续烂在池底。
建议**按到期紧迫度加权**(越临期权重越高)。
这样一来,骰子从「玩具」变成「清仓机制」,一举两得,而且用户感知不到任何复杂度。

**11.5 去重是最高性价比的一条防线。**
配额防不住「一个人反复加垃圾码」。`sha256(code)` 唯一索引能同时干掉:
重复提交、同一码被多个应用挂靠、以及把同一个码刷 50 遍的脚本。**服务端零成本。**

**11.6 需要一条反馈回路: 领取者能说「这个码是废的」。**
现在最大的体验断点是: 用户花掉 1/3 的额度,拿到一个用不了的码,然后**没有任何渠道表达**。
建议给每个应用一个**可用率**(有效领取 / 总领取),并在卡片上显示。
这不是防作弊,是**让供给质量可见**,让劣质来源自然沉底。

**11.7 补一层不需要 IP 的兜底。**
localStorage 一个字段就能做到: 首次访问生成一个随机 `browser_id` 存下来,
服务端按 `browser_id` 做**宽松**的日上限(比如单浏览器单日总领取 30 次)。
它拦不住决心绕过的人,但能让「写个循环刷」这件事从「5 行脚本」变成「要先清缓存」。
成本: 一个字段 + 一个计数。同时它给大盘提供了**去重后的访问量**。

**11.8 新应用待审要做「合并」而不是「新增」。**
否则一周后你会看到 5 个「ChatGPT」、3 个「Chat GPT」、2 个「chatgpt」。
提交时先按 `slug` 归一化匹配,命中已上架应用就直接把码挂上去(免审),
只有真的没命中才进待审队列。这一条能大幅减少管理员的队列长度。

**11.9 领取必须揭示「我拿到了什么」而不只是「复制成功」。**
复制成功是个弱反馈(用户不知道剪贴板里是不是对的)。
建议领取后给一张明确的确认卡: 应用名 + 码文(可手动选中)+ 到期时间 + 「已复制」。
这是把「一次给予」真正完成闭环的地方。

**11.10 无障碍与动效是硬门槛,不是加分项。**
`prefers-reduced-motion`、`:focus-visible`、`aria-live` 播报领取结果、剪贴板失败时的降级路径(手动选中)。
这些在 T11 里逐项验收。
